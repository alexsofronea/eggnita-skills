# Discovery — the six-question anchor intake

Before creating (or repositioning), find the **anchors** ([anchors.md](anchors.md)). Discovery is Fletch's "jargon → positioning" instrument: six ordered questions that surface the primary anchor containing a real problem. It's an adaptive dialogue, not a rigid form — infer from what the user gave, ask only the gaps, present each as selectable options with an escape, and let answers branch.

Same interaction contract throughout: recommend a default, offer the real alternatives, always allow "let me answer in my own words / talk it through." One question at a time; never dump all six.

## The six questions (in order)

The first three are the candidate **primary anchors** — you must pick **one** to root the positioning in, and it has to contain a fundamental problem.

1. **What category are we in?** → *Is there a big problem with the category itself, or with most competitors in it?* If yes, this is a primary-anchor candidate.
2. **What use case do we solve?** → *Is the way people/companies do this today broken?* If yes, candidate.
3. **Do we replace an alternative?** → *Is there a big problem with the current alternatives or a key competitor — a specific thing we replace?* If yes, candidate. If none of 1–3 has a real problem, there may be no wedge yet — surface that honestly.

→ **Pick ONE primary anchor** (category / use case / alternative) that holds a fundamental problem. The other two can still appear as support.

4. **What's the problem we solve?** → the problem at the heart of your primary anchor. *Describe it in 2–3 short sentences, no longer.*
5. **Who is it for, and who buys it?** → **company type** and **persona/department** (the secondary anchors — context, not the strategy). Who's underserved or gets the most value? Who *owns* the problem? Who's the buyer? *A few words each.*
6. **How do we solve it?** → the differentiation, in 2–3 sentences. How are you better/different than the rest of the category, the way the job is done today, or the alternatives? Name features if it helps.

Length is a signal: if the answers run much longer than this, the positioning isn't sharp enough yet.

## Also capture (lightweight)

- **Business type** — SaaS · services/consultancy · dev tool · marketplace · personal/bio · other. Drives the overlay in [patterns.md](patterns.md).
- **Proof** — logos, results, numbers, testimonials, credentials (feeds the Canvas features/benefits and the page's proof section).
- **Stage** — net-new, or repositioning something that exists (and why it isn't working → Stage 1 of [create.md](create.md)).

## How to run it

- **Infer first.** Read everything given (a URL, paste, description) and pre-fill. Only ask genuine gaps.
- **Selectable options + escape**, e.g.:
  > **Which primary anchor holds the real problem?**
  > - (A) *Use case: [inferred job] — because [the way it's done today is broken]* — recommended
  > - (B) *Category: [inferred category] — because [the category/competitors are flawed]*
  > - (C) *Alternative: [inferred incumbent] — because [it's painful in specific ways]*
  > - Let me talk it through
- **Let answers branch.** A services answer pulls the deliverables-heavy overlay; a dev-tool answer probes the technical-vs-buyer language gap.
- **Stop when you have the anchors + problem + differentiation** — enough to fill the Canvas. Don't complete the list for its own sake.
- **Echo back** the one-sentence explanation ([anchors.md](anchors.md)) built from their answers and confirm before moving on.

## The strategic calls discovery must surface

Some answers are decisions to reason through, not facts to log — use the models in [frameworks.md](frameworks.md):

- **Primary anchor = category vs. use case** → the maturity fork ([frameworks.md](frameworks.md#1)); this is the biggest call.
- **The alternative** → the real competition is usually the status quo, not a rival startup ([frameworks.md](frameworks.md#2)); build the JTBD map ([frameworks.md](frameworks.md#3)) and pick ONE to position against.
- **Who it's for** → anchor on use-case, not firmographics ([frameworks.md](frameworks.md#6)); confirm you're aiming at the *real buyer*, not the C-suite ([frameworks.md](frameworks.md#11)).
- **The problem** → check it has a clear owner ([frameworks.md](frameworks.md#5)); an unowned problem is a dead end however painful.

## Output

A confirmed set of anchors + problem + differentiation — the raw material the options map and Canvas in [create.md](create.md) are built from. No Canvas gets filled on unconfirmed assumptions.
